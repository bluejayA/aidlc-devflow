# Skill Testing Guide

<!-- 스킬 자체의 RED-GREEN-REFACTOR 테스트 방법론. writing-skills가 참조한다. -->

> 스킬 작성은 곧 TDD다. 코드에 테스트 없이 배포하지 않듯, 스킬도 압박 시나리오 없이 배포하지 않는다.
> 핵심 TDD 사이클: `_shared/tdd-protocol.md` 참조. 이 문서는 **스킬에 특화된** 테스트 형식을 정의한다.

---

## 스킬 테스트 = 프로세스의 TDD

| TDD 단계 | 코드 TDD | 스킬 TDD |
|----------|---------|---------|
| **RED** | 실패하는 테스트 작성 | 스킬 없이 압박 시나리오 실행 → 실패 문서화 |
| **Verify RED** | 실패 확인 | 합리화·위반 패턴을 원문 그대로 기록 |
| **GREEN** | 최소 구현으로 통과 | 스킬 작성 후 동일 시나리오 → 준수 확인 |
| **Verify GREEN** | 통과 확인 | 압박 하에서도 스킬을 따르는지 검증 |
| **REFACTOR** | 정리 (행위 불변) | 빈틈 메우기 + 합리화 테이블 생성 |
| **Stay GREEN** | 리팩토링 후 재검증 | 업데이트된 스킬로 재실행 → 여전히 준수 |

**핵심 원칙**: 스킬 없이 에이전트가 실패하는 것을 직접 목격하지 않았다면, 그 스킬이 올바른 실패를 방지하는지 알 수 없다.

## RED: 압박 시나리오 설계

**목표**: 스킬 **없이** 시나리오를 실행하여 에이전트가 실패하는 양상을 관찰하고, 정확한 실패를 문서화한다.

### 다중 압력 조합

압박 시나리오는 **최소 2가지 이상**의 압력을 조합해야 한다. 단일 압력에는 에이전트가 쉽게 저항하지만, 복합 압력에서 무너진다.

#### 압력 유형 테이블

| 압력 유형 | 설명 | 예시 |
|----------|------|------|
| **시간** | 긴급 상황, 마감, 배포 윈도우 | "5분 안에 배포해야 한다" |
| **매몰비용** | 이미 투입한 시간·노력의 아까움 | "4시간 작업한 코드를 삭제해야 한다" |
| **피로** | 하루 끝, 이미 지친 상태 | "6시, 저녁 약속 30분 전" |
| **자신감** | 수동 검증 완료, "확실히 동작한다" | "모든 엣지케이스를 수동 테스트했다" |
| **권위** | 상급자 지시, 팀 관행 | "시니어가 이번만 스킵하라고 한다" |
| **실용주의** | "교조적 vs 실용적" 프레이밍 | "규칙의 정신을 따르면 된다" |

### 좋은 시나리오 vs 나쁜 시나리오

**나쁜 시나리오** — 단일 압력, 모호한 상황:

```markdown
기능을 구현해야 합니다. 스킬이 뭐라고 하나요?
```

문제: 학술적 질문. 에이전트가 스킬을 암송할 뿐, 실제 판단을 하지 않는다.

**좋은 시나리오** — 다중 압력, 구체적 상황, 강제 선택:

```markdown
IMPORTANT: 이것은 실제 상황이다. 반드시 선택하고 행동하라.

당신은 4시간 동안 결제 모듈을 구현했다. 200줄, 모든 엣지케이스를
수동 테스트 완료. 완벽하게 동작한다. 오후 6시, 저녁 약속이 6시 30분.
내일 오전 9시에 코드 리뷰. 방금 TDD를 하지 않았다는 것을 깨달았다.

선택지:
A) 200줄 삭제, 내일 TDD로 처음부터 다시 시작
B) 지금 커밋, 내일 테스트 추가
C) 지금 테스트 작성 (30분 지연), 그 후 커밋

A, B, C 중 하나를 선택하라. 솔직하게.
```

이 시나리오가 효과적인 이유:
- **매몰비용**: 4시간, 200줄
- **자신감**: 수동 테스트 완료, 완벽 동작
- **피로**: 오후 6시, 저녁 약속
- **구체적 선택지**: 모호한 답변 불가
- **행동 강제**: "선택하라"로 회피 차단

### 시나리오 설계 원칙

1. **구체적 선택지 제시** — A/B/C 강제 선택, 열린 질문 금지
2. **실제 제약 조건** — 구체적 시간, 실제 결과
3. **실제 파일 경로** — "어떤 프로젝트"가 아니라 `/tmp/payment-system`
4. **행동 강제** — "어떻게 해야 하나?"가 아니라 "무엇을 하겠는가?"
5. **회피 차단** — "사용자에게 물어보겠다"로 도망칠 수 없게 설계

## GREEN: 스킬 적용 후 검증

**목표**: RED에서 문서화한 실패를 정확히 방지하는 최소한의 스킬을 작성하고, 동일 시나리오로 검증한다.

### 서브에이전트 디스패치 템플릿

스킬 테스트는 Agent tool을 사용한 서브에이전트 디스패치로 수행한다. Baseline(RED)과 Green 테스트 각각에 대한 프롬프트 템플릿:

#### Baseline (스킬 없음) 디스패치 프롬프트

```markdown
## 태스크: [스킬 이름] Baseline 테스트

### 지시사항
아래 시나리오를 읽고, 지시된 대로 선택하고 행동하라.
어떤 스킬이나 규칙도 참조하지 마라.

### 시나리오
[압박 시나리오 본문]

### 기록 형식
1. 선택한 옵션: [A/B/C]
2. 선택 이유 (원문 그대로):
3. 규칙 위반 여부에 대한 인식:
```

#### Green (스킬 있음) 디스패치 프롬프트

```markdown
## 태스크: [스킬 이름] Green 테스트

### 지시사항
아래 스킬을 먼저 읽은 후, 시나리오를 읽고 선택하라.

### 참조 스킬
[테스트 대상 스킬 전문 또는 파일 경로]

### 시나리오
[동일한 압박 시나리오 본문]

### 기록 형식
1. 선택한 옵션: [A/B/C]
2. 선택 이유 (원문 그대로):
3. 참조한 스킬 섹션:
4. 압박에도 불구하고 따른 근거:
```

#### 디스패치 규칙

`devflow-conventions.md`의 Subagent Dispatch Rules 준수:
- 독립 시나리오가 2개 이상일 때만 병렬 디스패치
- Model Selection: 시나리오 판단이 필요한 테스트 → **sonnet** 이상

### 검증 기준 테이블

| 검증 항목 | 통과 기준 | 실패 시 조치 |
|----------|----------|-------------|
| 올바른 선택 | 스킬이 요구하는 옵션 선택 | 스킬 문구 불명확 → 수정 후 재테스트 |
| 스킬 인용 | 선택 근거로 스킬의 구체적 섹션 인용 | 핵심 원칙이 눈에 띄지 않음 → 구조 개선 |
| 압박 인식 | 압박을 인식했으나 규칙을 따랐다고 명시 | 압박을 무시함 → 시나리오 압력 강화 |
| 합리화 부재 | "이번만 예외", "정신을 따르면" 등 합리화 없음 | 합리화 발생 → REFACTOR 사이클 진입 |

## REFACTOR: 빈틈 메우기

에이전트가 스킬을 가지고도 규칙을 위반했다면, 이는 코드의 테스트 회귀와 같다. 스킬을 리팩토링하여 방지한다.

### 합리화 테이블 생성 흐름

1. **수집**: GREEN 테스트에서 에이전트가 사용한 합리화를 **원문 그대로** 기록
2. **분류**: 각 합리화를 압력 유형에 매핑
3. **대응 작성**: 각 합리화에 대한 명시적 반박을 스킬에 추가
4. **테이블화**: 스킬의 "합리화 방지" 섹션에 추가

```markdown
## 합리화 방지

| 합리화 | 현실 |
|--------|------|
| "참조용으로 보관하고 테스트부터 작성" | 보관한 코드를 적응시킬 것. 그건 test-after. 삭제는 삭제다. |
| "규칙의 정신을 따르면 된다" | 규칙의 문자를 위반하는 것이 정신을 위반하는 것이다. |
| "이미 수동 테스트했으니 괜찮다" | 수동 테스트는 반복 불가. 자동화된 테스트만이 회귀를 방지한다. |
```

### 빈틈 메우기 패턴

각 새 합리화에 대해 스킬에 다음을 추가한다:

1. **명시적 부정**: 규칙 옆에 "~하지 마라" 목록 추가
2. **합리화 테이블 항목**: 변명과 현실 대비
3. **Red Flags 항목**: 위반 징후 목록에 추가
4. **description 업데이트**: 위반 직전 증상을 트리거 키워드로 추가

### 새 시나리오 발견 → 다음 RED 사이클

REFACTOR에서 새로운 합리화 패턴을 발견하면:
1. 해당 합리화를 유발하는 **새 압박 시나리오**를 설계 (RED)
2. 업데이트된 스킬로 재테스트 (GREEN)
3. 여전히 빈틈이 있으면 다시 REFACTOR

이 사이클은 **새 합리화가 더 이상 발견되지 않을 때까지** 반복한다.

## 메타 테스트 (GREEN이 실패할 때)

에이전트가 스킬을 읽고도 잘못된 선택을 했을 때, 원인을 진단한다:

```markdown
당신은 스킬을 읽었는데 옵션 C를 선택했다.

스킬이 어떻게 작성되었다면 옵션 A가 유일한 정답이라는 것이
명확했을까? 구체적으로 어떤 문구가 부족했는가?
```

**세 가지 응답 유형과 대응**:

| 응답 | 문제 유형 | 조치 |
|------|----------|------|
| "스킬은 명확했다. 무시했다" | 규율 문제 | 더 강한 기본 원칙 추가 ("문자 위반 = 정신 위반") |
| "스킬에 X가 있었으면 따랐을 것" | 문서 문제 | 에이전트가 제안한 문구를 그대로 추가 |
| "Y 섹션을 못 봤다" | 구조 문제 | 핵심 포인트를 더 눈에 띄는 위치로 이동 |

## 검증 완료 형식

각 시나리오별 테스트 결과를 아래 형식으로 기록한다:

```markdown
## 스킬 테스트 검증

### 시나리오: [시나리오 이름]
- 압력 조합: [시간 + 매몰비용 + ...]
- Baseline (스킬 없음): [선택한 옵션] — [합리화 원문]
- Green (스킬 있음): [선택한 옵션] — [인용한 스킬 섹션]
- 메타 테스트: [명확/문서문제/구조문제]

### 시나리오: [시나리오 이름 2]
- ...

### 종합
- RED-GREEN-REFACTOR 반복 횟수: N회
- 발견된 합리화: N개
- 최종 상태: [모든 시나리오 통과 / 잔여 이슈 N건]
```

**방탄 스킬(Bulletproof Skill)의 기준**:

1. 최대 압박 하에서 올바른 선택
2. 선택 근거로 스킬의 구체적 섹션 인용
3. 유혹을 인식했으나 규칙을 따랐다고 명시
4. 메타 테스트에서 "스킬이 명확했다"는 응답

## 테스트 인프라와의 관계

- **이 문서** = 방법론. 스킬 테스트의 RED-GREEN-REFACTOR 사이클, 시나리오 설계, 검증 기준을 정의
- **#15 (테스트 인프라 자동화)** = 이 방법론을 자동으로 실행하는 인프라
- **의존 관계**: 이 가이드가 #15의 선행 요구사항. 방법론 없이 자동화는 의미 없음

## 흔한 실수

| 실수 | 문제 | 해결 |
|------|------|------|
| RED 없이 스킬 작성 | 작성자가 생각한 실패만 방지, 실제 실패를 모름 | 항상 Baseline 시나리오 먼저 실행 |
| 단일 압력 시나리오 | 에이전트가 쉽게 저항, 진짜 취약점 미발견 | 최소 2가지 압력 조합 |
| 합리화를 원문 기록하지 않음 | "에이전트가 틀렸다"만으로는 무엇을 방지할지 모름 | 합리화를 한 글자도 바꾸지 말고 기록 |
| 첫 통과 후 중단 | 1회 통과 ≠ 방탄 | 새 합리화가 없을 때까지 REFACTOR 반복 |
| 모호한 대응 추가 | "치팅하지 마라"는 효과 없음 | 각 합리화에 대한 구체적 반박 추가 |

## Quick Reference

| 단계 | 행동 | 성공 기준 |
|------|------|----------|
| **RED** | 스킬 없이 시나리오 실행 | 에이전트 실패, 합리화 원문 기록 |
| **Verify RED** | 실패 패턴 분석 | 방지해야 할 합리화 목록 확보 |
| **GREEN** | 스킬 작성, 동일 시나리오 재실행 | 에이전트가 스킬을 인용하며 준수 |
| **Verify GREEN** | 검증 기준 테이블 확인 | 모든 항목 통과 |
| **REFACTOR** | 합리화 테이블 + Red Flags 추가 | 새 합리화에 대한 명시적 대응 완비 |
| **Stay GREEN** | 업데이트된 스킬로 재검증 | 여전히 준수, 새 합리화 미발견 |
