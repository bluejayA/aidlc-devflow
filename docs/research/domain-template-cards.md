## 카드 사용 흐름

1. 자기 과제 도메인을 5개 카드 중 하나에 매핑 (애매하면 가장 가까운 것 + 다른 카드 일부 차용 OK)
2. 각 §6-5 영역의 사례 문장을 **자기 과제 맥락으로 1-2줄 수정**
3. 카드 외 default 보강(§6-1/6-2/6-4 등)도 함께 적용
4. 자주 빠지는 함정 섹션 읽고 추가 점검

각 카드 작성 시간 목표: **5-10분**.

## 카드 A — SaaS / 외부 고객 서비스

> 적용 예: 외부 고객 대상 웹 서비스, 고객 대상 챗봇, 외부 API 서비스, B2B/B2C 일반 SaaS

**Tier 권장**: 표준 또는 고위험 (외부 고객 노출이면 최소 표준)

### §6-5 AI 금지 영역 사례

| 영역 | 사례 |
|------|------|
| **도메인 핵심 사실** | 가격 정책·SLA 약속·제품 설명 변경은 AI 자율 확정 금지. 마케팅·영업·법무 검토 거침 |
| **보안 경계** | 외부 노출 API의 인증·인가 로직 변경은 보안팀 사전 승인. 프롬프트 injection으로 사용자 데이터 추출 가능한지 사전 테스트 |
| **비용 상한** | 외부 사용자 호출 = 토큰 비용 직결. rate limit + 사용자별 quota를 AI 자율 결정 금지 |
| **데이터 접근 범위** | 다른 고객 데이터 cross-tenant 접근 절대 금지. RAG 시 tenant 경계 강제 |
| **고객 영향 결정** | 사용자에게 노출되는 텍스트(에러 메시지, 안내문, 약관 인용) AI 자율 변경 금지 — 법적·브랜드 영향 |
| **레거시 breaking change** | 공개 API 응답 스키마·webhook payload 변경은 deprecation 6개월 + 명시적 마이그레이션 가이드 |

### Doc 3 default 보강 (이 도메인 특화)

- §6-2 데이터·보안: **테넌트 격리 enforcement 필수**, 사용자 입력 sanitize layer
- §6-4 인간 승인: 가격/SLA/약관 텍스트 변경, public API 변경 추가
- §6-9 비용: 사용자별 quota + DDoS 보호 (악의적 사용자가 토큰 폭증시키는 시나리오)

### 자주 빠지는 함정

- 데모/내부 테스트 단계에서 cross-tenant 격리 검증을 빼먹음 → 베타 직전 발견
- "고객은 우리 의도대로 쓸 것"이라는 가정 → 프롬프트 injection으로 시스템 프롬프트 추출 시도 발생
- 무료 사용자가 토큰 비용을 폭증시키는 시나리오 미고려

### v1.1 신규 — Multi-party approval 권장

| Tier | 권장 승인 | 구성 |
|------|--------|-----|
| 표준 | 단일 | 기술 리더 |
| 고위험 | **2-party** | 기술 리더 + 보안/법무 (공개 API 변경, 가격·SLA 변경) |
| Critical (드뭄) | 3-party | + 마케팅 (약관·브랜드 문구) |

### v1.1 신규 — 도메인별 DoD 확장

- **Accessibility 준수** (WCAG 2.1 AA 이상, 고객 대면 시)
- **i18n 검증** (다국어 UI 시)
- **부하 테스트** (사용자 동시 접속 예상치 × 1.5)
- **Rate limit 검증** (사용자별 quota 정확 작동 테스트)

### v1.1 신규 — 시뮬레이터 / Legacy-brief

- 시뮬레이터: 해당 없음 (대부분)
- Legacy-brief: 구 API 버전 유지·마이그레이션 필요 시 구 스키마 brief 작성

### v1.1 신규 — Shadow / Canary 권장

- **Shadow**: 고위험 시 2주 (기존 비공개 환경 트래픽 복제)
- **Canary**: 고위험 시 5% 사용자로 1주 (A/B test 활용)

## 카드 B — 사내 생산성 도구

> 적용 예: 사내 검색, 회의록 자동 정리, 코드 리뷰 보조 챗봇, 사내 문서 Q&A, 슬랙 봇

**Tier 권장**: 경량 또는 표준 (외부 노출 없으면 경량 가능)

### §6-5 AI 금지 영역 사례

| 영역 | 사례 |
|------|------|
| **도메인 핵심 사실** | 사내 정책·인사 규정·법무 가이드 인용은 AI 자율 확정 금지. 원문 링크 + AI는 요약만 |
| **보안 경계** | SSO 연동 우회·권한 escalation 코드 AI 자율 작성 금지. 사내 시스템 호출 allowlist 유지 |
| **비용 상한** | 사내 사용자 수 × 호출 빈도 산정. 무한 루프 방지 timeout |
| **데이터 접근 범위** | 인사·재무·법무 문서 등 권한 없는 카테고리 접근 금지. RAG 인덱싱 대상 사전 승인 |
| **고객 영향 결정** | 사내 의사결정에 영향을 주는 답변(예: "이 결정 OK인가요?") AI 자율 답변 금지. 참조 자료 제시까지만 |
| **레거시 breaking change** | 다른 사내 시스템과 연동된 부분(예: Slack notification 형식) 변경은 사용자 공지 필수 |

### Doc 3 default 보강

- §6-2 데이터·보안: SSO 연동, 사내 계정 권한 매핑 검증
- §6-4 인간 승인: RAG 인덱싱 대상 추가, Slack/이메일 자동 발송 활성화
- §6-9 비용: 사용자당 일일 호출 상한

### 자주 빠지는 함정

- "사내용이니까 보안 약해도 됨" 안이함 → 권한 escalation 사고
- 인덱싱 대상에 인사·재무 문서가 섞임 → 권한 없는 사용자에게 노출
- 사용자 수 100명 가정했는데 실제 500명 → 비용 5배 폭증

### v1.1 신규 — Multi-party approval 권장

| Tier | 권장 승인 | 구성 |
|------|--------|-----|
| 경량·표준 (대부분) | **단일** | 기술 리더 |
| 고위험 (드뭄) | 2-party | 기술 리더 + 보안/인사 (인덱싱 대상 확장 시) |

### v1.1 신규 — 도메인별 DoD 확장

- **RAG 품질 지표**: 검색 정확도 (top-3 hit rate), 답변 관련성 (사용자 피드백 ≥ 4/5)
- **인덱싱 대상 범위 감사 로그** (카테고리별 접근 가능 사용자 명시)
- **권한 escalation 테스트** (권한 없는 사용자 시나리오 5개)

### v1.1 신규 — 시뮬레이터 / Legacy-brief

- 시뮬레이터: 해당 없음
- Legacy-brief: 사내 기존 시스템(ERP / HRIS 등) 연동 시 legacy-brief 권장 (권한 구조 특이)

### v1.1 신규 — Shadow / Canary 권장

- **Shadow**: 선택 (1주, 파워 유저 10명 내부 베타)
- **Canary**: 선택 (일부 팀 먼저)

## 카드 C — 데이터 파이프라인 / 분석

> 적용 예: ETL 자동화, 데이터 품질 검증, 분석 리포트 자동 생성, 이상 탐지, 대시보드 데이터 가공

**Tier 권장**: 표준 (분석용은 표준, 운영 의사결정 자동화면 고위험)

### §6-5 AI 금지 영역 사례

| 영역 | 사례 |
|------|------|
| **도메인 핵심 사실** | 비즈니스 지표 정의(예: "활성 사용자" 기준)는 AI 자율 변경 금지. 데이터팀 합의된 정의 고정 |
| **보안 경계** | 원본 데이터 소스 접근 권한·query 범위 AI 자율 확장 금지. 읽기 전용 권한 유지 |
| **비용 상한** | 대용량 query 토큰·BigQuery scan 비용 자동 사전 추정 + 임계 초과 시 사람 승인 |
| **데이터 접근 범위** | PII 컬럼은 마스킹 후 AI 전달. 원본 SSN·계좌·전화번호 직접 노출 금지 |
| **고객 영향 결정** | 분석 결과를 자동으로 사용자/외부에 push하는 액션(예: 알림, 청구 조정) AI 자율 금지 |
| **레거시 breaking change** | 기존 리포트·대시보드 스키마 변경은 다운스트림 영향 분석 필수 (BI 도구 깨짐) |

### Doc 3 default 보강

- §6-2 데이터·보안: PII 마스킹 layer, 원본 데이터 dry-run query 강제
- §6-4 인간 승인: 새 데이터 소스 추가, 자동 액션 활성화
- §6-9 비용: query당 sample size 제한, full-scan 사전 경고

### 자주 빠지는 함정

- AI가 컬럼명만 보고 의미 추정 → 잘못된 지표 정의 양산
- "분석만 한다"고 시작했는데 점차 자동 액션이 추가되며 위험 누적 (scope creep)
- 대용량 데이터 sampling 없이 전체 query → 비용 폭증

### v1.1 신규 — Multi-party approval 권장

| Tier | 권장 승인 | 구성 |
|------|--------|-----|
| 표준 | 단일 | 데이터팀 리더 |
| 고위험 (자동 액션 포함) | **2-party** | 데이터팀 리더 + 하류 시스템 소유자 (재무·운영·마케팅 등) |
| 규제 대상 (금융·의료) | 3-party | + 법무/규제 |

### v1.1 신규 — 도메인별 DoD 확장

- **데이터 품질 검증** (결측·중복·범위 체크 자동화)
- **다운스트림 영향 테스트** (BI 대시보드·리포트 스키마 호환성)
- **샘플링 강제** (full-scan query 금지, 샘플 size 명시)
- **지표 정의 changelog** (비즈니스 지표 변경 시 이력 감사)

### v1.1 신규 — 시뮬레이터 / Legacy-brief

- 시뮬레이터: 해당 없음 (분석 도메인)
- Legacy-brief: **원본 데이터 소스 스키마 brief 필수** (업스트림 시스템별 컬럼 의미·제약 조건 기술)

### v1.1 신규 — Shadow / Canary 권장

- **Shadow**: 표준 이상 **필수 1-2주** (새 집계 로직 vs 기존 결과 비교)
- **Canary**: 선택 (자동 액션 포함 시 필수, 5% 사용자)

## 카드 D — 클라우드 인프라 운영 (네트워크 자동화 포함)

> 적용 예: K8s 운영 자동화, 자동 스케일링, 인시던트 자동 대응, 로그 분석, **네트워크 장비(switch/router/firewall) 설정 자동화**, BGP/VLAN 변경, 방화벽 규칙 관리

**Tier 권장**: 표준 또는 고위험 (네트워크·방화벽·프로덕션 인프라는 고위험)

### §6-5 AI 금지 영역 사례

| 영역 | 사례 |
|------|------|
| **도메인 핵심 사실** | 네트워크 토폴로지·라우팅 정책·SLA 약속은 AI 자율 확정 금지. 네트워크팀·SRE 검증 필수 |
| **보안 경계** | 방화벽 규칙·NACL·security group 변경은 AI 자율 적용 금지. 변경 전 `dry-run` + 사람 승인 |
| **비용 상한** | 자동 스케일링 상한·인스턴스 타입 변경 AI 자율 결정 금지. 월 인프라 예산 hard cap |
| **데이터 접근 범위** | 프로덕션 DB·secret store 접근은 read-only + 감사 로그. 자격 증명 직접 출력 금지 |
| **고객 영향 결정** | 트래픽 영향 있는 변경(BGP 라우팅, DNS, load balancer 재구성)은 maintenance window + 사람 승인 |
| **레거시 breaking change** | 네트워크 명령 한 줄 잘못 = 망 전체 다운. 모든 변경 `staging → canary → prod` 단계 강제. 롤백 절차 사전 확보 |

### Doc 3 default 보강

- §6-2 데이터·보안: kubeconfig·CLI 자격 증명 격리, 모든 명령 감사 로그
- §6-4 인간 승인: 프로덕션 변경, 네트워크 장비 명령, 방화벽 규칙 변경 추가
- §6-9 비용: 자동 스케일링 상한, 인스턴스 타입 화이트리스트

### 네트워크 자동화 특화 추가 사항 (별도 카드 아닌 D 안에서)

- **명령 dry-run 의무화**: AI가 생성한 모든 네트워크 명령은 `--dry-run` 또는 시뮬레이터 통과 후 적용
- **변경 영향 범위 사전 표시**: "이 명령으로 영향받는 호스트/세션 수 N개" AI가 사전 산정
- **비상 롤백 명령**: AI 변경 명령마다 즉시 롤백 가능한 reverse 명령 함께 생성
- **네트워크 망 분리**: 관리망(management plane)과 데이터망(data plane) 명령 분리, AI는 management만

### 자주 빠지는 함정

- "테스트 환경에서 됐으니 prod도 되겠지" → BGP/방화벽은 토폴로지 의존성으로 prod 특이 케이스 발생
- AI가 명령 syntax는 맞게 생성하나 의도 다른 명령 (예: ACL deny 위치 잘못) → 정상 트래픽 차단
- 롤백 명령 미리 안 만들어 둠 → 사고 시 복구 30분 → 1시간으로 폭증
- 권한이 너무 강한 토큰을 AI가 들고 있음 → 잘못된 명령 한 번에 전체 클러스터 영향

### v1.1 신규 — Multi-party approval 권장

| Tier | 권장 승인 | 구성 |
|------|--------|-----|
| 표준 | 2-party | 기술 리더 + SRE |
| 고위험 (일반 K8s 운영) | **2-party** | 기술 리더 + SRE |
| **Critical (네트워크 장비, 방화벽, BGP)** | **3-party** | 네트워크 리더 + SRE + 보안 |

### v1.1 신규 — 도메인별 DoD 확장

- **장비 OS × 버전 매트릭스 테스트** (3종 × 3버전 이상)
- **시뮬레이터 100% 통과** (GNS3 / EVE-NG / CML / Cisco Modeling Labs)
- **롤백 훈련 완료** (팀 전원 실 장비 롤백 모의 훈련 1회 이상)
- **영향 범위 사전 산정** (명령별 영향 장비·세션·트래픽 수 기록)
- **dry-run 커버리지 100%** (모든 운영 명령)

## 카드 E — 빌링 / 미터링 / 재무 연동

> 적용 예: 사용량 미터링, 청구서 자동 생성, 결제 시스템 연동, 환불·할인 처리, 회계 시스템 데이터 export, 세무 신고 데이터 가공

**Tier 권장**: **고위험 기본** (금전·감사·고객 청구 영향 + PII 결합)

### §6-5 AI 금지 영역 사례

| 영역 | 사례 |
|------|------|
| **도메인 핵심 사실** | 미터링 단위(GB·시간·요청수), 비례 배분 규칙, 청구 주기, 환불·할인 정책은 AI 자율 확정 금지. 재무팀 검증 필수 |
| **보안 경계** | 결제 자격 증명·카드 정보·계좌 정보 AI 노출 금지 (PCI DSS). API 인증(OAuth/HMAC) 약화 금지 |
| **비용 상한** | 잘못된 청구서 sanity check (전월 대비 ±N% 초과 시 자동 중단). **토큰 비용보다 청구 금액 정확성**이 더 critical |
| **데이터 접근 범위** | 사용량 raw 데이터에 AI 접근은 집계·익명화 후만. 고객 식별자 + 금액 결합 노출 절대 금지 (cross-tenant 누설 사고 직결) |
| **고객 영향 결정** | 청구 금액·환불·할인 정책 변경 절대 AI 자율 금지. 기존 청구 형식·webhook 변경은 사용자 자동화 깨짐 |
| **레거시 breaking change** | 청구서 포맷·webhook payload·API 응답 스키마 변경은 deprecation **6개월 이상** + 명시적 마이그레이션 + 회계 감사 가능성 유지 |

### Doc 3 default 보강

- §6-2 데이터·보안: PCI DSS 준수, PII + 금액 결합 최소화, 모든 변경 audit log
- §6-4 인간 승인: 청구 정책 변경, 환불 정책 변경, 새 결제 수단 추가, 청구서 포맷 변경
- §6-9 비용: 청구서 발급 전 sanity check 의무화, 이상 청구 사전 차단

### 자주 빠지는 함정

- "사용량만 측정한다"로 시작했는데 자동 청구 발급으로 scope creep → 사람 승인 단계 누락
- AI가 미터링 단위 잘못 해석 (예: GB-hour vs GiB-hour) → 청구 오차 누적
- 재계산·환불 시 audit log 부족 → 사후 분쟁 시 증거 부재
- 잘못된 청구서 발급 → 고객 항의 + 회계 정정 + 법적 리스크 동시 발생
- 청구서 포맷 무단 변경 → 고객 자동화(SAP, ERP 연동) 깨져 N일간 청구 누락
