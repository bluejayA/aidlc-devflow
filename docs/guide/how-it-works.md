# AIDLC와 함께 개발하기

> 아이디어 하나로 시작해서, AI와 대화하며 소프트웨어를 완성하는 과정을 소개합니다.

---

## 한눈에 보는 전체 흐름

```
💡 아이디어  →  📋 설계  →  🔨 개발  →  ✅ 완성
   "이런 거      AI가 질문하며     테스트부터      빌드·검증 후
    만들고 싶어"   함께 정리        코드 작성       머지 결정
```

AIDLC는 소프트웨어를 만드는 전 과정에서 AI가 파트너로 함께합니다.
각 단계마다 **AI가 먼저 초안을 만들고, 내가 확인하고 승인하는** 구조입니다.
승인 없이 다음 단계로 넘어가지 않기 때문에, 항상 내가 흐름을 주도합니다.

---

## 1단계: 아이디어를 말한다

> "사용자 로그인 기능을 만들고 싶어"

이 한 마디로 시작합니다. AI가 알아서 코드를 짜기 시작하는 게 아닙니다.
대신, **필요한 것들을 질문으로 정리**해줍니다.

### AI가 하는 일
- 프로젝트가 새로 시작하는 건지, 기존 코드에 추가하는 건지 파악
- 요청이 모호하면 구체적인 질문을 던짐
  - "소셜 로그인도 포함하나요?"
  - "비밀번호 찾기 기능은 필요한가요?"
- 요구사항을 문서로 정리

### 내가 하는 일
- 아이디어를 자유롭게 설명
- AI의 질문에 답변
- 정리된 요구사항이 맞는지 확인하고 승인

### 이 단계가 끝나면
- 무엇을 만들지 명확하게 정리된 문서가 생깁니다
- 요청의 복잡도에 따라 분석 깊이가 자동으로 조절됩니다
  - 간단한 기능 → 빠르게 정리하고 넘어감
  - 복잡한 시스템 → 사용자 스토리, 비기능 요구사항까지 꼼꼼히 정리

---

## 2단계: 설계를 함께 만든다

> "어떤 구조로 만들지 AI가 초안을 잡고, 내가 방향을 잡아준다"

요구사항이 확정되면, AI가 **어떻게 만들지** 계획을 세웁니다.

### AI가 하는 일
- 어떤 단계를 거칠지 실행 계획 수립
- 필요하면 컴포넌트 구조, 서비스 설계 초안 작성
- 큰 작업은 독립적으로 개발할 수 있는 단위로 분해

### 내가 하는 일
- 실행 계획 검토 — 단계가 너무 많으면 줄이고, 빠진 게 있으면 추가
- 설계 방향이 마음에 들지 않으면 수정 요청
- 최종 승인

### 이 단계가 끝나면
- 승인된 실행 계획과 설계 문서가 준비됩니다
- "무엇을 만들지"와 "어떻게 만들지"가 모두 확정된 상태입니다

---

## 3단계: 코드를 만든다

> "테스트를 먼저 쓰고, 통과하는 코드를 만드는 방식으로 안전하게 개발"

설계가 승인되면, AI가 코드를 작성하기 시작합니다.
하지만 무작정 코드부터 쓰지 않습니다.

### AI가 하는 일
- **테스트를 먼저 작성** — "이 기능이 제대로 동작하면 이런 결과가 나와야 한다"
- 테스트를 통과하는 코드를 작성
- 코드 작성 전에 계획을 먼저 보여주고 승인을 받음
- 필요하면 기존 코드를 안전하게 보호하기 위해 별도의 작업 공간에서 개발

### 내가 하는 일
- 코드 작성 계획 검토 및 승인
- 생성된 코드가 의도에 맞는지 확인
- 중간에 방향을 바꾸고 싶으면 언제든 조정 가능

### 왜 테스트를 먼저 쓸까?
- "동작하는 것 같아요"가 아니라 **"테스트가 통과했으니 동작합니다"**
- 나중에 다른 기능을 추가할 때 기존 기능이 깨지는 걸 자동으로 감지
- AI가 작성한 코드를 사람이 일일이 검증하지 않아도 테스트가 품질을 보장

---

## 4단계: 완성한다

> "빌드하고, 테스트하고, 코드에 합치는 것까지"

코드 작성이 끝나면, 마지막 검증과 마무리를 진행합니다.

### AI가 하는 일
- 전체 빌드 실행 — 컴파일 오류나 의존성 문제 확인
- 전체 테스트 실행 — 모든 기능이 정상 동작하는지 확인
- 빌드·테스트 지침 문서 자동 생성

### 내가 하는 일
- 빌드·테스트 결과 확인
- 코드를 메인 브랜치에 합칠지, PR을 만들지, 보관할지 결정

### 이 단계가 끝나면
- 테스트를 통과한, 바로 사용할 수 있는 코드가 완성됩니다
- 모든 설계 결정과 진행 과정이 문서로 남아있습니다

---

## AIDLC만의 특징

다른 AI 코딩 도구와 무엇이 다른지, 각 단계에서 어떤 기술적 장치가 동작하는지 소개합니다.

---

### 오케스트레이터가 전체를 관리한다

일반적인 AI 코딩 도구는 요청마다 독립적으로 동작합니다. AIDLC는 다릅니다.

**하나의 오케스트레이터(`aidlc-using-devflow`)가 전체 라이프사이클을 소유**합니다.
각 세부 스킬은 맡은 일만 하고 결과를 돌려주며, 오케스트레이터가 승인 게이트 제시, 상태 업데이트, 감사 로그 기록, 다음 단계 라우팅을 모두 처리합니다.

```
[오케스트레이터]
  └─ 반복:
      1. 세부 스킬 호출 → 결과만 받음
      2. 감사 로그 기록
      3. 승인 게이트 제시 (A: 수정 / B: 다음으로)
      4. 상태 업데이트
      5. 라우팅 테이블로 다음 단계 결정
```

이 구조 덕분에:
- 전체 흐름을 한 곳에서 파악할 수 있고
- 새로운 단계를 추가할 때 라우팅 테이블만 수정하면 되고
- 문제가 생겼을 때 오케스트레이터 하나만 추적하면 됩니다

---

### 적응형 깊이 — 요청에 맞게 절차가 달라진다

모든 요청에 같은 절차를 적용하지 않습니다. 요청의 복잡도에 따라 **3단계 깊이**가 자동 결정되고, 각 깊이에서 실행되는 스테이지가 달라집니다.

| 깊이 | 언제 적용되나 | 실행되는 스테이지 |
|------|-------------|----------------|
| **Minimal** | 단순하고 명확한 요청 (버그 수정, 설정 변경) | 요구사항 분석 → 바로 코드 작성 |
| **Standard** | 일반적인 기능 추가 | 요구사항 분석 → 실행 계획 → 코드 작성 |
| **Comprehensive** | 다중 컴포넌트, 외부 연동, 고위험 | 요구사항 분석 → 사용자 스토리 → 비기능 요구사항 → 컴포넌트 설계 → 단위 분해 → 상세 기능 설계 → 코드 작성 |

Comprehensive에서만 실행되는 조건부 스테이지들:
- **사용자 스토리 변환** — 요구사항을 INVEST 기준의 사용자 스토리로 정리
- **비기능 요구사항 수집** — 성능, 보안, 확장성 같은 품질 속성을 별도로 정리
- **컴포넌트 설계** — 서비스 구조와 의존 관계를 설계
- **단위 분해** — 큰 시스템을 독립적으로 개발 가능한 Unit으로 분리
- **상세 기능 설계** — 도메인 엔티티, 비즈니스 규칙, 데이터 흐름을 정의

---

### Brownfield 자동 분석 — 기존 코드베이스를 먼저 파악한다

새 프로젝트가 아니라 기존 코드에 기능을 추가하는 경우, AI가 먼저 프로젝트 현황을 파악합니다.

- **Technology Stack 수집** — `package.json`, `go.mod`, `pyproject.toml` 등 매니페스트를 파싱하여 프레임워크, 빌드 도구, 테스트 프레임워크, 린터를 자동 식별
- **Code Structure 분석** — 디렉토리 구조, 진입점, 아키텍처 패턴(MVC, 레이어드 등)을 파악

기존 코드를 모른 채 새 코드를 작성하는 실수를 방지합니다.

---

### TDD Iron Law — 테스트 없는 코드는 작성하지 않는다

AIDLC는 TDD(Test-Driven Development)를 **선택이 아닌 규칙**으로 강제합니다.

```
🔴 RED     — 실패하는 테스트를 먼저 작성
🟢 GREEN   — 테스트를 통과하는 최소한의 코드 작성
🔵 REFACTOR — 동작을 유지하면서 코드 개선
```

- 실패하는 테스트 없이는 프로덕션 코드를 작성하지 않음
- 코드 작성 후 자체 리뷰(Self-Review)를 수행
- "테스트 나중에 쓸게요" 같은 합리화를 구조적으로 차단

---

### 2단계 코드 생성 — 계획 먼저, 코드는 승인 후

AI가 바로 코드를 생성하지 않습니다. **Plan → 승인 → Generate** 2단계로 나뉩니다.

1. **Plan 단계** — 어떤 파일에 어떤 코드를 작성할지 계획서를 먼저 제출하고 멈춤
2. **승인** — 계획이 적절한지 검토. 수정 요청 가능
3. **Generate 단계** — 승인된 계획에 따라 코드를 작성

AI가 의도와 다른 방향으로 대량의 코드를 생성하는 것을 사전에 방지합니다.

---

### Git Worktree 격리 — 기존 코드를 안전하게 보호한다

코드 작성을 시작하기 전에, **별도의 Git Worktree(작업 공간)를 생성**하여 격리된 환경에서 개발합니다.

- `main` 브랜치는 항상 안전한 상태를 유지
- 새 기능 개발이 기존 코드에 영향을 주지 않음
- 문제가 생기면 워크트리를 버리고 다시 시작 가능

---

### 서브에이전트 병렬 실행 — 큰 작업을 나눠서 동시에 처리한다

복잡한 작업은 **독립적인 서브에이전트가 태스크를 나눠서 동시에 실행**합니다.

- 각 서브에이전트는 독립된 컨텍스트에서 하나의 태스크만 담당
- 완료된 결과는 2단계 리뷰(스펙 준수 → 코드 품질)를 거침
- 순차적으로 하나씩 처리하는 것보다 빠르게 결과를 냄

---

### 세션 연속성 — 대화가 끊겨도 이어서 작업한다

AI와의 대화 세션이 끊기거나 새로 시작해도, **이전에 어디까지 진행했는지 자동으로 파악**합니다.

- `devflow-state.md`에 현재 Phase, Stage, 진행 상태가 기록됨
- 세션 재개 시 이전 산출물을 자동으로 로딩
- 마지막으로 완료한 태스크를 재검증하여 정합성 확인

"어디까지 했더라?"를 사람이 설명하지 않아도 됩니다.

---

### 체계적 디버깅 — 증상이 아니라 원인을 찾는다

버그가 발생하면, AI가 바로 코드를 수정하지 않습니다.

1. 증상을 기록하고
2. 가설을 세우고
3. 가설을 검증할 수 있는 방법으로 원인을 좁혀가고
4. 원인이 확인된 후에야 수정

"일단 고쳐봤는데 안 되네요"를 반복하지 않습니다.

---

### 완료 전 검증 강제 — "될 것 같아요"는 허용하지 않는다

AI가 "완료했습니다"라고 말하기 전에, **실제로 검증 명령을 실행**해야 합니다.

- 빌드가 성공하는지 직접 실행
- 테스트가 통과하는지 직접 실행
- 회귀 테스트까지 RED-GREEN 검증

추측이 아니라 실행 결과로 완료를 증명합니다.

---

### 워크플로우 자체도 검증한다

AIDLC는 사용자의 코드만 검증하는 것이 아닙니다. **AIDLC 워크플로우 자체의 정확성도 자동으로 검증**합니다.

오케스트레이터의 분기 로직, 라우팅 경로, 스텝 순서를 메타 태그로 정의하고, 테스트 인프라가 이를 정적으로 검증합니다:
- 막다른 경로(dead-end)가 없는지
- 도달 불가능한 단계가 없는지
- 실행 순서가 올바른지

워크플로우 자체에 버그가 숨어 있는 것을 방지합니다.

---

## 핵심 원칙 3가지

### 1. 항상 내가 주도한다
매 단계마다 AI가 "이렇게 할까요?"라고 묻고, 내가 승인해야 다음으로 넘어갑니다.
AI가 임의로 결정하고 진행하는 일은 없습니다.

### 2. 모든 과정이 기록된다
요구사항, 설계, 코드 계획 — 모든 결정이 문서로 자동 저장됩니다.
나중에 "왜 이렇게 만들었지?"라는 질문에 문서가 답해줍니다.

### 3. 복잡도에 맞게 조절된다
간단한 버그 수정에 과한 절차를 거치지 않습니다.
반대로, 복잡한 시스템은 빠뜨리는 것 없이 꼼꼼하게 진행합니다.

| 요청 예시 | AI의 판단 | 진행 방식 |
|----------|----------|----------|
| "버튼 색상 변경" | 간단 | 빠르게 요구사항 정리 → 바로 코드 작성 |
| "로그인 기능 추가" | 보통 | 요구사항 분석 → 설계 → 코드 작성 |
| "결제 시스템 구축" | 복잡 | 사용자 스토리 → 비기능 요구사항 → 상세 설계 → 단위별 코드 작성 |
